# 地图编辑源交付规范

给制作地图的美术看。按本文交付的存档，烘焙器（`:baker`）能直接烘成服务器用的地图版本；不合规的存档会被烘焙器拒收，并给出出错的区块坐标。

对应需求：`docs/DESIGN-M3.md` 的 `REQ-M3-020`、`REQ-M3-022` 与 `API-M3-003`；远景（第 3 节大区对齐、第 5 节隐藏区域）对应 `REQ-M3-024` 与 `API-M3-014`。本文随烘焙器的规则更新，两者不一致时以烘焙器的实际行为为准，并回来改本文。

## 1. 存档要求

| 项 | 要求 | 不满足时 |
| --- | --- | --- |
| 游戏版本 | 原版 Java 版 26.2 存档，每个区块的 `DataVersion` 都是 4903 | 退出码 2。比 4903 旧时提示先升级（第 2 节第 1 步）；比 4903 新时是被更新版本的游戏打开过，原版不会降级，只能换回最后一次用 26.2 打开的备份 |
| 生成状态 | 交付范围内每个区块都生成到 `minecraft:full` | 退出码 2，给出该区块坐标 |
| 区块压缩 | `server.properties` 的 `region-file-compression` 保持默认 `deflate` | LZ4 压缩的区块退出码 2。已写成 LZ4 的区块不会因为改了设置就重写：改回 `deflate` 后用原版 26.2 专用服务端 `java -jar server.jar --forceUpgrade --recreateRegionFiles nogui` 重写一遍，再自检 |
| 超大区块 | 不能有外置的 `.mcc` 区块文件（单个区块超过 1 MiB 时原版会外置） | 退出码 2，给出该区块坐标。减少这个区块里的方块实体、实体或物品数据，直到原版把它存回区域文件 |
| 方块与生物群系 | 只用原版 26.2 的方块和生物群系，不装任何增加方块或群系的模组、数据包 | 退出码 2，给出未知的名字 |
| 维度 | 地图做在主世界（`dimensions/minecraft/overworld/`） | 找不到该维度时退出码 2 |
| 可用高度 | 所有方块、方块实体（箱子、告示牌等）和实体（展示框、盔甲架等）都在 **y −64 到 191** 之内，共 256 格。y 192 到 319 必须全是空气 | 退出码 2，报出区块坐标、越界的方块或实体和它的 y |

服务器的世界只有 256 格高，烘焙器只取 y −64 到 191 这一段。原版主世界最高到 y 319，自然生成的高山可能伸到 y 192 以上，交付前用 WorldEdit 把这些山顶削掉。y −64 的基岩层和地下的深板岩都在范围内，不用动。

整张图都要做在更高处时（比如浮空岛），可以让程序用 `--min-y` 把这 256 格整体上移，例如 `--min-y 0` 取 y 0 到 255，那时 y 0 以下也必须全是空气，包括原版的基岩与深板岩。`--min-y` 必须是 16 的倍数，交付时说明用的是哪个值。

## 2. 处理顺序

交付前按顺序做完下面三步，顺序不能换：

1. 存档来自旧版本时，先用原版 26.2 专用服务端升级：`java -jar server.jar --forceUpgrade --eraseCache nogui`，等它跑完退出。存档被比 26.2 新的版本打开过时，原版不会把它降回 26.2，只能换回最后一次用 26.2 打开的备份，所以不要用比 26.2 新的客户端打开地图。
2. 用原版 26.2 专用服务端加 Chunky 把交付范围预生成一遍，直到范围内每个区块都是 full，且原版光照已算完（区块的 `isLightOn` 为真）。**升级之后必须重跑这一步**：升级只改数据格式，不补生成。
3. 用烘焙器自检（见第 6 节）。退出码 0 才算可以交付。

预生成时范围外会留下一圈没生成完的区块，这是正常的。交付时说明范围（见第 3 节），烘焙器只检查范围内的区块。

## 3. 交付范围

交付时给出地图的区块坐标矩形：最小 x、最小 z、最大 x、最大 z，四个数都是区块坐标（方块坐标除以 16 向下取整），含边界。例：方块 x 0～4,095、z 0～4,095 对应区块 `0,0,255,255`。

烘焙器用 `--bounds 0,0,255,255` 接收这个范围。不给范围时，烘焙器取存档里所有区块的外接矩形，预生成留下的外圈会让它拒收。

### 大区、出生点与关卡门

一张地图分成几个大区（正式档每个大区 4,096 × 4,096 格）时，交付时另给下面三样。它们不写进存档，由运维写进分片目录 `shards.json`（`docs/DESIGN-M3.md` `API-M3-010`），写错了分片起不来并报出是哪一项。

| 项 | 要求 |
| --- | --- |
| 大区范围 | 每个大区一个区块坐标矩形，写法同上面的交付范围；都在交付范围之内、彼此不重叠；做成正方形，不是正方形时世界边界按长边画，玩家能走出短边：先进至多 17 个区块的只读邻区，再往外是空气区块，到世界边界才被拉回。四条边最好落在 256 区块的整倍数上（区块坐标 0、256、512…，即方块坐标 4,096 的整倍数）：远景按这样对齐的 4,096 × 4,096 格方块下载，对齐时玩家进一个大区只下一块完整的，不对齐时要下 2～4 块；大区四周 4,096 格以内的方块只下 16 格一个点的粗略版，远景因此能越过大区边界画到相邻大区 |
| 关卡门 | 所在大区、门框两个对角的方块坐标（x、y、z，含边界）、通往哪个大区。整个门框在本大区之内、在可用高度（第 1 节）之内；同一大区的门框互不重叠；两个大区之间最多一扇门。门框只是一个判定范围，玩家从框外走进框内就被送往目标大区，框里放什么方块由美术决定 |
| 到达点 | 每扇门一个：x、y、z 与朝向。从这扇门通往的那个大区走回来的玩家出生在这里，所以它要在本大区之内、不在任何门框里，脚下能站人；离门框留几格，玩家落地后要先走出再走进才会再被送走 |

玩家登录时出生在所在大区中心区块的中心那一列（方块坐标 x、z 各为该区块起点加 8），站在那一列的地表上。这一列要能站人，也不能落在本大区任何门框的 x、z 范围里：分片按列判、不看高度，门框就算只占这一列的地下或高空也会拒启。

大区边界两侧各 16 格（一个区块）以内不放玩家能放置或破坏的方块。分片只重算并写入本大区内区块的光照，边界另一侧是邻区的只读区块，光照停在烘焙值；边界 16 格内的改动会在边界上留下一道光照接缝，邻区的分片也看不到这次改动（`docs/DESIGN-M3.md` §28.1「大区边界附近的改方块」）。

## 4. 制作工具

默认 WorldEdit 7.4.5 + Litematica 0.28.8，地形底稿可以用 WorldPainter（它对 26.2 的支持还没核实，用前先出一小块走一遍第 2、6 节）。工具选择还在等拍板（`docs/DESIGN-M3.md` §28.1 F3），改了会更新本节。

## 5. 服务端数据标记

需要服务器处理的方块（带逻辑的门、战利品箱等），用 **DATA 模式的结构方块** 标出来。结构方块放在目标方块**正上方一格**，在结构方块界面里把模式切到 DATA，「元数据」一栏按下面的格式填：

```
<命名空间> <SNBT>
```

- 命名空间是程序登记过的处理器名，例如 `synaxis:door`。可用的名字由程序提供清单；写了清单上没有的名字，烘焙器退出码 2，并报出结构方块坐标和这个名字。
- SNBT 是这个方块的服务端数据，可以省略。例：`synaxis:door {locked:1b}`。
- SNBT 里不能写 `id`、`x`、`y`、`z` 这四个键，位置由结构方块决定。
- 目标方块本来就有方块实体时（比如箱子），SNBT 的内容合并到它原有的数据上，原有的物品、名字等保留。
- 结构方块正下方不能是另一个数据标记。
- 烘焙后结构方块本身变成空气，玩家看不到。

例：一扇门的下半格在 (10, 63, 10)、上半格在 (10, 64, 10)，DATA 结构方块放在 (10, 65, 10)，元数据 `synaxis:door {locked:1b}`。烘焙后 (10, 65, 10) 是空气，门的上半格带上 `synaxis:door` 处理器和 `locked:1b`。门这类两格高的方块只能标上半格，因为下半格的正上方就是它自己的上半格。

### 隐藏区域

远景（远处的地形轮廓）里不想让玩家提前看到的区域，用同样的 DATA 结构方块圈出，元数据写：

```
synaxis:hidden <x1> <z1> <x2> <z2>
```

四个数是方块坐标，两个角都包含在内。这个结构方块也会变成空气，可以放在烘焙范围（`--bounds`）以内的任意区块里；放在范围外的不会被读到，圈的区域也不会被替换。圈出的区域压到烘焙范围外的那部分，远景里本来就是空的。远景里这些区域显示成一块平地：高度取区域外紧挨着的一圈地表里最低的那一处，材质是石头，颜色按平原算。区域贴着烘焙范围的边时，只看范围以内的那一圈（范围外没有地表）；区域盖满了整个烘焙范围、范围以内一圈都没有时，高度按 0 算。远景每 4 × 4 格取一个点，区域边缘压到的那一小块整块替换，所以远景里被抹平的范围最多比圈出的范围每边宽 3 格。从相邻大区远望时用的是每 16 × 16 格（一个区块）一个点的粗略版，同样整块替换，被抹平的范围按区块对齐，最多每边宽 15 格。区域本身在地图里照原样保留，玩家走近以后照常看得到。

## 6. 自检

在仓库根目录执行。`<存档目录>` 是含 `level.dat` 的那一层；两个目录都写绝对路径，`:baker:run` 在 `baker/` 子目录里运行，相对路径会找错地方。`<地图名>` 只用小写字母、数字、`_` 与 `-`，以字母或数字开头，至多 32 个字符（如 `arena`、`castle_v2`）：它是输出目录名，也是远景下载地址的一段。

```
./gradlew :baker:run --args="bake --map-id <地图名> --source anvil:<存档目录> --bounds <minX,minZ,maxX,maxZ> --out <输出目录> --threads 8"
```

可用高度按第 1 节上移过时，在 `--args` 里加 `--min-y <值>`。

| 退出码 | 含义 | 怎么办 |
| --- | --- | --- |
| 0 | 烘焙成功，输出目录下出现 `<地图名>/<build_id>/` | 可以交付 |
| 1 | 命令行写错：地图名不合上面的写法、选项拼错或给了两次、选项不属于这个命令、数值不是整数；或者游戏模块里两个处理器同名、有处理器加载不了 | 按错误信息改命令行，错误信息之后打印着用法与各选项的默认值；处理器同名或加载不了时找程序。烘焙器什么都没写 |
| 2 | 存档不合格：版本不对、区块没到 full、范围内缺区块、压缩格式不对、区块数据损坏、标记写错、可用高度之外有东西 | 按错误信息里的区块坐标或结构方块坐标修改。信息里有 `does not decode` 时是这个区块的数据坏了：换回存档备份；没有备份时用 MCA Selector 删掉这个区块，再按第 2 节重跑预生成 |
| 3 | 某个区域烘焙失败，例如一个 16×16×16 的小节里用了超过 256 种方块状态，一个区块的数据包超过 8 MiB（多是放了大量装满成书的箱子），或一个方块实体的数据太大（如塞满写字成书的箱子，信息里有 `does not read back`）；也可能是输出目录写不进 | 错误信息逐行列出每个失败的区域：按坐标减少该处的方块种类或带数据的方块；方块实体的数据太大时信息末尾有区块内位置 `(block entity at x …, y …, z … of the chunk)`，把那里的东西拆到几个容器里；其余情况找程序。信息以 `cannot` 开头（`cannot create`、`cannot write`、`cannot assemble`）时没有坐标，是输出目录的问题：查 `--out` 的权限和剩余空间，然后重跑。`<地图名>/` 下留着一个 `.baking-*` 隐藏目录供排查（`cannot create the work directory` 时没有），大小接近整张图，路径打在 stderr 的 `baker: kept … for inspection` 一行里，排查完删掉 |
| 4 | 烘焙结果自检不通过；也可能是自检之后输出目录写不进 | 信息以 `cannot` 开头（`cannot write the manifest`、`cannot publish`）时是输出目录的问题：查 `--out` 的权限和剩余空间，然后重跑。其余情况找程序，这是烘焙器的问题。`<地图名>/` 下同样留着一个 `.baking-*` 隐藏目录，路径打在 stderr 的 `baker: kept … for inspection` 一行里，交给程序排查后删掉 |
| 5 | 同一内容的地图版本已经在输出目录里 | 不用重烘；要重烘就换输出目录 |
| 6 | 烘焙器的光照版本还没通过验证 | 找程序 |

烘焙器认得的处理器命名空间来自游戏模块：程序在游戏模块里登记一个处理器，自检命令就认得它的名字。游戏模块现在登记了两个：`synaxis:door` 与 `synaxis:loot`，目前只作标记，服务器还不按它们执行玩法。除第 5 节隐藏区域的 `synaxis:hidden` 外，数据标记写了这两个以外的名字，自检以退出码 2 报「not registered」，并给出结构方块坐标和这个名字；需要新名字时找程序登记。

退出码 0 时，清单 `manifest.json` 里的 `verify.source_light_diff` 是烘焙器算出的光照与原版光照不同的格数。结构方块换成空气后，它自己那一格和正下方一格的光照必然变，这两格不计入；其余的差异交给程序看，不影响交付。

烘焙器每个线程约需 256 MB 内存。`:baker:run` 默认能用本机物理内存的四分之一，8 GB 内存的机器用 `--threads 8` 够用。退出码 3 且错误信息里有 `OutOfMemoryError` 时，把 `--threads` 减半重跑。

## 7. 实体

展示框、盔甲架、文字展示（`*_display`）这类静态实体照常在游戏里摆放，烘焙器把 `entities/` 里的实体原样带进地图。玩家进入区块时，服务器只生成下表这六种，每种只还原表里列出的内容：

| 实体 | 还原的内容 |
| --- | --- |
| `item_frame`、`glow_item_frame` | 位置与朝向、挂的物品、物品的旋转、是否隐形 |
| `text_display` | 位置与朝向、文字、面向玩家的方式（`billboard`）、背景色 |
| `item_display` | 位置与朝向、显示的物品 |
| `block_display` | 位置与朝向、显示的方块 |
| `armor_stand` | 位置与朝向、小号、显示手臂、不显示底座、`Marker`、是否隐形 |

以下内容不还原：画、生物、矿车等其他实体与 `interaction`；盔甲架的装备；实体的自定义名字（`CustomName`），悬浮文字改用 `text_display` 做；骑在别的实体上的乘客（`Passengers`），叠成一组的几个展示实体要分开摆；展示框里地图的画面。它们烘焙时不报错，进了服务器也不出现，交付前按上表自查。

玩家在游戏里打掉或改动生成的实体，区块重新载入后会复原。用 NBT 编辑器改过的实体要保留 `Pos`（三个数）与 `Rotation`（两个数）：缺了、个数不对或不是有限数时，烘焙器退出码 2，报出区块坐标和实体 id。
