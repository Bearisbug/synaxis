# Minestom 审计总结与开发计划（2026-09-09）

对象：`Bearisbug/Minestom`（fork 自 `Minestom/Minestom` master，HEAD `16842f1954`，2026-09-04）。
方法：6 个 Opus 5 agent 按子系统只读审计源码并复核上游 issue / PR，主管单独跑基线构建与测试，并对各报告最严重的结论逐条对照源码核实，其中一条实跑复现。

## 一、结论

1. **Minestom 可以作为我们的基座，但不能不打补丁直接上生产。** 单线程逻辑与协议编解码质量高，2480 个测试全绿；问题集中在并发生命周期、错误路径和 tracker 回收三类，共确认 15 条 P0。
2. **有 3 条 P0 会在最普通的使用里出现**：玩家走动即触发 `EntityTracker` 无界泄漏；从 tick 线程停服必死锁；默认配置下事件分发在无锁地并发读 `WeakHashMap`。前两条上游 issue 已挂 1 到 2 年无人处理。
3. **有 4 条 P0 是远程可触发的**：一个零长包或一个自嵌套的药水组件就能让读线程抛异常或 `StackOverflowError`，抢跑一个配置包能让服务器丢整 tick，背包拖拽越界能复制物品。做对外服务前必须修。
4. **上游的修复能力不差但注意力极窄**：PR 合并中位 2 天，但 80 个 open PR 中 47 个已冲突，68 个 open bug 中 88% 半年无人回应。寻路、视野/乘客、背包事务、Batch、命令回调、停服生命周期六个领域上游三年没动，必须自己扛。
5. **对我们的游戏是好消息**：不要原版玩法意味着上述六个领域里寻路、背包事务、乘客、动态光照四个可以直接绕开而不是修，真正必须修的是线程、事件、tracker、网络四层的基础缺陷。

## 四、逐层一句话

- **网络层**（01）：写路径与 232/238 个包的往返测试很扎实，问题全在错误分支，「解析失败、缓冲不足、状态机被客户端抢跑」三类几乎没设计过。
- **实体层**（02）：单线程逻辑尚可，并发模型是虚的。`acquirable-strict` 的 `assertOwnership()` 全仓库零调用，测试 JVM 里开着的安全网从未生效。
- **instance 层**（03）：坐标、位打包、碰撞的数学质量高；缺陷全在「谁持锁、future 失败谁兜底、缓存谁回收」。另有一条光照边界错误，主世界最上面三个 section 没有跨 section 传播。
- **线程/事件层**（04）：三个 P0 都是结构性的，且 jcstress 现有 11 个场景里没有一个覆盖它们。
- **物品/命令/编解码层**（05）：37 条发现，shift 点击、双击、拖拽三种模式零集成测试，P0 正落在这些空白里。
- **质量工程**（06）：errorprone 100 多项且 `-Werror` 很强，但 jcstress 与 JMH 不在 CI 里，`testing/` 框架断言对象不断言字节，握手、登录、压缩、加密零集成覆盖。

## 六、开发计划

### 阶段 0：工程基线（本周）

- 分支策略：`master` 只跟 upstream，我们的补丁放 `fork/main`，每次上游打 tag 后 rebase 一次。
- 把镜像脚本用法与 JDK 25 要求写进 fork 的 README；构建命令固定为带 `--init-script gradle-init/aliyun-mirror.init.gradle.kts`。
- CI 加两道上游没有的门：jcstress 进 CI，JaCoCo 只对新增行设阈值。
- 合入上述 5 个上游 PR。

### 阶段 1：止血（1 到 2 周）

按第三节的顺序修前 12 条，每条先落 agent 给出的失败测试再修，并发类的补 jcstress 场景。修复量都很小：

- 第 1 条去掉 `shutdown()` 的 `synchronized` 并在 `stop()` 末尾 join 线程。
- 第 2 条 `ChunkViewKey` 改值比较、空桶删除、加注销路径，同时吸收 `fix/viewable-leak`。
- 第 3 条 `WeakHashMap` 换 `HashMap` 快照，第 4 条删掉 `:539` 的锁外 `invalidate()` 或改成 volatile record。
- 第 5 条 `thenRun` 改 `whenComplete`，第 6 条把光照重算移出写锁区间。
- 第 7、8 条续体切回 tick 线程执行并加 `isRemoved()` 检查。
- 第 9 到 12 条各是几行边界检查加深度上限。

其中 1、3、10 这三条小而确定，修完先以 PR 提回上游，减少长期 rebase 负担。

### 阶段 2：绕开而不是修（与阶段 1 并行决策）

上游三年不动的六个领域，对我们的游戏逐个判断：

| 领域 | 我们的处理 |
|---|---|
| 寻路 / Navigator | 不用。RTS 单位和 MMORPG 怪物的寻路本来就要自研，基于我们自己的导航网格 |
| 背包事务 | 不用原版背包语义。自定义 UI 走自己的数据模型，只把 Minestom 的 inventory 当显示层 |
| 视野 / 乘客 | 少用。单位用 display 实体，乘客关系只在必要处出现 |
| 动态光照 | 关掉。自研地图预烘焙光照，运行时不重算，第 6 条 P0 随之失效 |
| Batch API | 不依赖。地图加载走 Polar 格式整块载入 |
| 命令回调 | 不依赖。游戏内交互走自定义包，不走聊天命令 |

这一步的意义是把「必须修」的清单压缩到线程、事件、tracker、网络四层。

### 阶段 3：游戏垂直切片（阶段 1 收尾后启动）

- 仓库形态：Gradle 多模块 `common` / `server` / `client`，`server` 通过 `includeBuild` 依赖本 fork。
- 第一个切片：RTS 镜头下选中一个单位，点地面让它走过去。打通镜头、输入、自定义协议、服务端寻路、客户端渲染五个环节。
- 按全局约定，切片开工前先出设计文档，锁定客户端路线、数据模型、协议格式。
