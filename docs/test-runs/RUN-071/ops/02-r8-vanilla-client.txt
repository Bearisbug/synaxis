## reading
- The screen and the WARN line take the reason Connection#handleDisconnection read. It is null, shown as "Disconnected", whenever
  disconnectionDetails was not set by the time the main thread's Connection#tick saw the channel closed.
- Path 1, the disconnect packet never arrives: the server closes the socket, Netty reads the end of the stream, closes the channel and
  then fires channelInactive -> disconnect(endOfStream), which stores nothing because the channel is already closed. "Disconnected" is
  certain on this path.
- Path 2, the packet arrives: handleDisconnect -> Connection#disconnect on the Netty thread closes the channel, waits, and only then
  stores the reason. If the main thread's tick checks isConnected() inside that window, it handles the disconnection with no reason:
  "Disconnected" again. The window is the few steps of a channel close on the event loop; nothing the server does changes it.
