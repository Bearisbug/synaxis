# Findings
- Engine defect, fixed: once a connection is offline the write thread (Server#playerWriteLoop) flushed once more and closed the
  channel. One flushSync writes at most one buffer (16,383 bytes from the pool by default), so a disconnect packet queued behind more
  than that never left: the peer read the end of the stream. The write thread now calls PlayerSocketConnection#flushRemaining, which
  flushes until the queue and the leftover buffer are empty; a peer that does not read is still cut off by the closer thread after 1 s.
- R8 of run 37423439285 attempt 1 ("R8 FAIL screen: Connection Lost. Disconnected", once in 83 runs of the workflow, the rerun green):
  not closed. "Disconnected" is the vanilla client's text for a connection that ended without a reason. Two paths give it and the
  artifact cannot tell them apart: the disconnect packet never arrived (the defect above is one sure way there, on a 2 core runner
  whose client reads slowly), or it arrived and the client's render thread saw the channel closed in the window between the Netty
  thread closing it and storing the reason. Registered in docs/TEST.md §7 with what to record to decide the next time.
- Engine defect, fixed after review (662f645ea4): a disconnect on the write thread itself (a non-IO throwable in the write loop, a
  PlayerPacketOutEvent listener kicking) started no closer thread, and flushRemaining then wrote the whole queue: a peer that reads
  nothing kept the write thread in a blocking write with no end. flushRemaining now starts the closer thread before it writes.
- p10.py shards now chmods shards.json to 0644; before, the mode followed the umask (0664 under 002, 0600 under 077).
