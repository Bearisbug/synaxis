How long the tick of the core world waits while chunks generated after the start are lit (TC-PROD-720 step 5). server-app
test source set, CoreLightStallProbe (source next to this file), copied in for the run and deleted after; the probe the only
class of the run. The stdout lines are read from server-app/build/test-results/test/
TEST-io.github.bearisbug.synaxis.app.CoreLightStallProbe.xml. Code under test: 969cf2ce3b's CoreMode (HEAD 9dda638b08,
unchanged by this probe).

Why the tick waits (code, not measured): LightingChunk lights a chunk generated out of the lit ring when its first packet is
built (DynamicChunk#createChunkPacket -> LightingChunk#createLightData, LightingChunk.java:273 and :280 -> relightSection,
which runs inside synchronized (instance), :635). InstanceContainer#tick enters the same monitor every tick to clear
currentlyChangingBlocks (InstanceContainer.java:783-785), and the server tick ticks the instances before the dispatcher
ticks the chunks and entities (ServerProcessImpl.java:681-683). One relightSection covers more than one chunk:
collectRequiredNearby (:603-622) walks the 3 x 3 x 3 neighbourhood breadth first and takes in every loaded section still
waiting for its light; block light is not filtered by height (only sky light is, :587).

What the probe does: CoreMode.start on the Env's process (view distance 8, ring 361 chunks), then, out of the ring, one batch
after another: a 5 x 5 warm-up at chunk (0, 100); a 23 x 23 square (529 chunks, the ring of view distance 10) at (100, 0);
four columns of 23 chunks at x 112 to 115 (z -11 to 11), next to that square, one after another; then (run 2 only) squares at
(-100, 0), (0, -100), (0, 60) and four columns at x -112 to -115. Each batch is loaded first (loadChunk(...).join() on the
test thread), then a virtual thread builds the packets of the batch nearest first, as a player's chunk queue sends them and
off the tick thread like a connection's write thread, while the test thread calls InstanceContainer#tick once a millisecond
and times each call. first_packet_ms is the first packet's build, all_packets_ms the whole batch, longest_tick_ms the longest
tick call, ticks_over_50ms the tick calls over 50 ms, ticked_ms the tick calls summed.

For the 529-chunk batches the longest tick is 1.2-2.0 ms below the first packet's build: the first packet's relightSection
lights the whole batch while it holds the monitor. The later packets of a batch hold it only for the sky light of their two
sections above the floor (the sections the sky light filter at :587 leaves out of the walk), which the code shows and the
probe does not separate.

What it does not cover: a real connection's write thread (the probe's builder is a virtual thread of its own), chunk loading
and packet building interleaved as they are around a moving player (each batch here is loaded completely first, the worst
case for one hold), more than one builder at a time, and the strict and grid modes.
