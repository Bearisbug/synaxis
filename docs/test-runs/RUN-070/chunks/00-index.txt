# What the code did before the fix (src/main/java/io/github/bearisbug/synaxis/entity/Player.java of 14437d0b78)
- The queue is two structures under chunkQueueLock: chunkQueue, a LongArrayPriorityQueue ordered by Manhattan distance to the center
  the client was last sent (every dequeue scans the whole array and shifts it), and queuedChunks, a LongOpenHashSet that keeps a chunk
  from being queued twice. sendChunk enqueues; the chunk adder calls it once the ring's load completes: on the tick thread when the
  chunk was loaded already, otherwise on the virtual thread that completed the load.
- sendPendingChunks (every player tick) returns at once while chunkBatchLead >= maxChunkBatchLead. Each batch adds one to the lead,
  each ChunkBatchReceived (ChunkBatchListener -> onChunkBatchReceived) takes one off and sets the rate, clamped to 0.01..max-per-tick;
  maxChunkBatchLead is 1 until the first receipt, 10 after. So a client that never answers gets the first batch (9 chunks with the
  engine default, 4 on a shard host) and nothing more: measured, 9 chunk packets in 30 ticks of walking (01, 02).
- Out-of-ring entries were dropped only when dequeued (isOutOfClientRange). With nothing dequeued, every chunk the ring passes over
  stays: 2r + 1 entries per chunk travelled, all of them out of the ring once the player is r + 1 chunks further.
- After a later receipt the first send dequeues the closest chunks first and, once the ring is sent, every remaining out-of-ring entry
  in that same tick, each dequeue scanning the queue: 387 ms for 20,000 entries, 1,592 ms for 40,000, 6,643 ms for 80,000 (04).
- How large it gets depends only on where the player can go: before finding 1's fix a move is not checked against the world border or
  a per packet distance, so there is no bound; with that fix (64 blocks a packet, no crossing of the border outwards) a 4k x 4k block
  region (256 x 256 chunks) allows (256 + 2r)^2 = 79,524 entries at r = 13 (computed, not run), and the engine's default border
  (59,999,968 blocks wide) none. A tick handles at most 50 packets (synaxis.packet-per-tick); a 64 block packet adds 4 x 27 = 108 at
  r = 13 (04: 50 packets, 720 -> 6,120 entries, 130,280 bytes in the two arrays).

# The fix (5a084b973e): Player#sendPendingChunks first calls trimChunkQueue, which drops the out-of-ring entries once the queue holds more
# than (2r + 1)^2. It runs on the player's tick thread only, after the ring has moved; the queue is then within the ring before every send.
