Checked and left without a case (PlayClient.java at 62ae65f89c), in three kinds.

Nothing the host sends or the mod calls reaches them:
  - The fallbacks for a prop of another value type (:308, the instanceof of :313, :316, the instanceof of :324,
    :329): API-PLAY-003 makes a declared prop with another value type malformed, so the Widget record refuses it
    in the decoder and these never see one.
  - The fallbacks for a missing prop (:309, the orElse(false) of :313, :317, the orElse(0) of :324, :330): the
    Widget record checks the type of each prop it carries but asks for none, so the decoder takes a v1 widget with
    props missing. The host never sends one: WidgetEncoder encodes through the four factories Widget.text, timer,
    scoreboard and panel only, and each sets every prop of its kind.
  - click() with no scene (:443, scene_seq 0): its only caller is a PanelScreen button, and PanelScreen.sync opens
    a PanelScreen only when panel() gives a panel, which needs a scene. The scene goes back to null only in reset(),
    which runs from ClientPacketListener's constructor (ClientPlayConnectionEvents.INIT) at the end of a
    configuration phase, and each way into one has replaced the open screen first (javap of the 26.2 client jar):
    a new connection or a transfer goes through ConnectScreen.startConnecting, which calls
    Minecraft.disconnectWithProgressScreen and then Gui.setScreen with the ConnectScreen; a reconfiguration goes
    through ClientPacketListener.handleConfigurationStart, which calls Minecraft.clearClientLevel with a
    ServerReconfigScreen. So no PanelScreen is open while the scene is null.
  - Scene.owner()'s "colon < 0" (:82): the host takes every scene id from PlayIds.qualify (SceneService.java:217),
    which always gives <plugin_id>:<name>.
  - result()'s "scene != null" (:347): a key's action goes out only with a scene, and reset(), the one call that
    sets the scene back to null, clears the actions still waiting for a result at the same time.
  - remainingMs()'s check for an entry that is not a TIMER (:545): PlayHud.blocks calls it for TIMER entries only,
    and the gametest only after its own check for a TIMER.
  - receive()'s default branch (:269): it does nothing, for the two upward messages.

Changing them changes no reading:
  - Math.max(0, ...) on ttl_ms and remaining_ms (:311, :312): a TEXT with ttl <= 0 never expires either way; a
    stopped TIMER below 0 is drawn as 0:00 by PlayHud.clock (PlayHudTest theTimeLeftIsMinutesAndSecondsRoundedUp).
  - reset()'s "sets = 0" (:602) and forget()'s dismissed.remove() (:303): SET numbers only rise within a
    connection, so the next SET of a removed address outnumbers what dismissed keeps, and the mod compares them
    only within one connection, reset() clearing dismissed, the refused panel and the waiting actions. Across
    connections only PlayTestHook compares them: without "sets = 0" a recording started before a server switch
    would no longer miss the new connection's first SETs, and no script starts one there (DESIGN-PLAY §6.4.8).
  - cool()'s "cooldownMs > 0" (:394): with 0 the deadline is now, so the time left is 0 either way.
  - panelResult()'s OK with the panel no longer in the table (:377): recording the clicked SET in dismissed anyway
    ("panel == null || panel.set() == sent.panelSet()") keeps an entry whose number is below that of every later
    SET of the address, and reset() clears it, for the reason given for forget() above.
    anOkForAPanelNoLongerInTheTableChangesNothing pins what can be read: no exception (counter-proof E), the table
    stays empty and the panel's next SET shows.

Only tests call them:
  - texts()'s "instanceof Text" (:507) and cooldownLeftMs()'s "left > 0" (:558): neither the mod's main code nor
    the gametest calls these two methods (PlayTestHook.texts goes through PlayHud.blocks), so the product reads
    the same whatever they return.
