## 1. 结论

1. **区块包体比报告小一半**：高 384 自然地形压缩后 2,582 B/区块（带光照，均值），报告是 5,255 B。包体主要由地下内容决定：同一地表、地下无矿无洞时只有 906 B；高 256（Q7 默认）自然地形 1,502 B、实心地下 583 B。光照只让压缩包多 47～96 B（均值）。
2. **首次序列化与报告一致**：不带光照 0.77～0.94 ms/区块（报告 0.84）；LightingChunk 懒算光照的首次序列化每区块花 4.9～5.1 ms CPU（报告 5.18），墙钟 6.4～7.2 ms。光照已算好时只剩编码，0.82～0.94 ms。
3. **存活堆比报告小一半，差额来自口径**：高 384 自然地形 DynamicChunk 27.0 KiB/区块，算完光照 32.0 KiB。报告的 57 / 64 KiB 与本程序「序列化后、包缓存还在」的 48.9 / 55.0 KiB 吻合：`CachedPacket` 用 SoftReference 留着整个 `ChunkDataPacket`，里面是未压缩的 section 字节（约 19～25 KB/区块）。
4. **生成器用 `setAll` 会让堆涨 3 倍**：`PaletteImpl#setAll` 对非单值 section 直接转成 15 bit 直接调色板，高 384 自然地形因此从 27.0 涨到 81.1 KiB/区块，压缩包从 2,486 涨到 3,651 B。M2 的 `MapGenerator` 用 `fillHeight` + `setBlock`，走间接调色板，不受影响。
5. **整图 relight 比报告慢，且墙钟超线性**：高 384 自然地形 16,384 区块 6.2～12.7 s 墙钟、22.8～24.8 s CPU（报告 4.08 s）。CPU 接近线性（1,024 区块时 1.0～1.3、16,384 区块时 1.4～1.5 ms CPU/区块），墙钟超线性，因为 16,384 区块时只用上约 2～3.7 个核。relight 的堆增量与高度无关：4,096 区块时高 64 / 256 / 384 分别 13.2 / 14.9 / 14.9 MiB，因为只有地表附近约 1.1～1.5 个 section 留下天光数组。
6. **3×3 局部重算**：负载较轻的第 2 轮，高 384 懒重算中位 3.0 ms、P95 4.7 ms、最大 21.7 ms；负载重的第 1 轮中位 7.4 ms、P95 23.7 ms、最大 108.5 ms。报告的 3～43 ms 落在两轮之间。
7. **高 64 / 高 384 反常是口径混用，不是高度效应**：同口径下高 384 的整图堆是高 64 的 2.7～3.4 倍。报告的 78 MiB 与高 64 带包缓存（19.9 KiB × 4,096 = 80 MiB）吻合，46 MiB 与高 64 不带包缓存（11.3 KiB × 4,096 = 45 MiB）吻合，见第 5 节。

**耗时数字的限制**：两轮都在别的任务并行时跑。第 1 轮没有逐作业记录负载，结束时 1 / 5 / 15 分钟负载为 75 / 77 / 47；第 2 轮逐作业记录的 1 分钟负载为 26～58（12 核）。未压缩包体的长度分布两轮完全一致，压缩包在个别作业上有 0.003～0.033 B 的均值差（原因与修复见 §3.5，取整后本文数字不受影响），堆读数差 ≤ 1 KiB/区块；墙钟耗时两轮之间差到 2 倍，只能当上界用。relight 的 CPU 时间两轮差 1%～36%，比墙钟稳，估算烘焙成本时用 CPU 时间。

## 2. 方法

| 项 | 取值 |
| --- | --- |
| 机器 | Apple M4 Pro，12 核，24 GiB，macOS 15.3.2（aarch64） |
| JVM | OpenJDK 25.0.4.1；每个作业一个子 JVM：`-Xms6g -Xmx6g -XX:+UseG1GC -XX:+AlwaysPreTouch` |
| 预热与重复 | `packet`：1 轮预热 + 3 轮测量，每轮新建世界；`relight`：先整图 relight 一张 32×32 世界预热，再 3 轮测量；`local`：60 次改动预热 + 300 次测量 |
| 样本 | `packet` 的逐区块分布取每轮内圈 30×30 = 900 个区块、3 轮合计 2,700 个；边上一圈缺邻居，不计 |
| 测堆 | `System.gc()` 两次后读 `totalMemory - freeMemory`（与 `Match#sampleLiveHeap` 同法，没触发回收就报错），同一 JVM 内建世界前后相减再除以区块数。另用反射数出每区块的调色板形态与保留的光照数组个数（`breakdown` 字段） |
| 包体 | `CachedPacket#body(PLAY, registries, 256)` 的可读字节数，即成帧 + zlib 后真正写进 socket 的字节，压缩阈值取引擎默认 256 |
| 调色板 | 默认 `opt`：生成后逐 section `optimize(SIZE)`，等于从网络格式解码得到的间接调色板，也就是 .synx 加载后的形态；`setall` 保留生成器原样 |

地形由 `SyntheticTerrain` 按坐标确定性生成，三种：

| 名称 | 内容 |
| --- | --- |
| natural | 两层值噪声高度场（丘陵 + 山地），高 ≥ 256 时地表约 y=42～156、海平面 62；基岩、y<0 深板岩、石头、3 层泥土、草、沙滩、水；约 1.2% 石头换成矿石；噪声隧道；约每两个区块一棵橡树（只在区块内圈 12×12 列、海面 +1 以上放，每列概率 1/256，上限 0.56 棵/区块） |

### 3.5 字节复现

**修复前**：同一作业在不同 JVM 里跑，未压缩包体的长度分布完全一致，压缩后的长度分布在部分作业上不同。第 2 轮对第 1 轮，`setall` 的不带光照 / 带光照压缩包均值差 0.0044 / 0.0033 B，flat40 差 0.033 / 0.020 B，高 256 natural 差 0.0033 / 0.0033 B，其余 4 个作业一致；集成分支 RUN-026 的复跑也是这样。原因在引擎：`ChunkData` 的构造器用 `Map.copyOf` 复制高度图、用 `Collectors.toUnmodifiableMap` 复制方块实体，编码器按迭代顺序写出。这两种不可变 Map 的迭代顺序由每个 JVM 启动时的随机种子决定，所以同一区块状态在两个 JVM 里编出长度相同、字节不同的包（高度图两项互换位置），压缩后长度随之变化。压缩本身是确定的。

**修复**：`5fba33a398` 把两个 Map 改成按高度图类型序号、方块索引排序的 `EnumMap` 与 `TreeMap`，由 `ChunkPacketDeterminismTest` 起 6 个子 JVM 逐字节比对守住。基准 `f5a99ee031` 起在 `packet` 作业里给测量区块的成帧包与未压缩包各算一个 SHA-256（字段见 jmh-benchmarks/README.md），字节复现改以摘要为判据。

**修复后**：连续两次跑 7 个 `packet` 作业（`bench-2026-09-packet-canonical-1/2.json`，1 分钟负载第一次 14.7～29.1、第二次 9.4～14.1，12 核），28 个摘要两次全部相同。与两份旧 JSON 比，未压缩长度分布全部相同；压缩长度分布在高 256 natural 上与第 1 轮差 0.0033 B（均值）、在 `setall` 与 flat40 上与第 2 轮差 0.003～0.033 B，其余作业与两轮都相同，即旧 JSON 的这几个作业恰好抽到了与修复后相反的顺序。§3.1 表中取整后的数字都不变，本文没有改动任何表格数字。

**代价**：包的长度不变。交替跑修复前后各 3 次（高 384 natural 与高 64 flat40 两个作业，负载 8～13），高 384 natural 首次序列化中位数修复前 0.490～0.502 ms、修复后 0.503～0.505 ms，光照已知时 0.460～0.465 对 0.464～0.468 ms，差在 0.015 ms 以内，与同组内的波动同量级。这 6 次的原始 JSON 未入库。修复前 3 次里 flat40 的 4 个摘要与修复后不同、高 384 natural 相同，即那几个 JVM 恰好抽到了与修复后相反 / 相同的高度图顺序；未压缩摘要不同而长度相同，正是只比长度发现不了的情形。

## 5. 高 64 世界 4,096 区块 78 MiB、高 384 只有 46 MiB 的反常

本次同口径的数（4,096 区块，MiB）：

| 口径 | 高 64 natural | 高 64 flat40 | 高 384 natural |
| --- | --- | --- | --- |
| relight 堆增量 | 13.2 | 12.2 | 14.9 |
| 光照后世界合计，间接调色板 | 45（11.3 KiB/区块） | 41 | 124 |
| 光照后世界合计，setAll 直接调色板 | 96 | 88 | 330 |
| 光照后 + 包缓存（1,024 区块世界的 KiB/区块 × 4,096） | 80（19.9 KiB） | 68 | 220 |

同口径下高 384 的世界合计是高 64 natural 的 2.7～3.4 倍，relight 增量与高度无关，所以「高 384 比高 64 省」在任何单一口径下都不成立。报告的两个数分别与高 64 的两种口径吻合：78 MiB ≈ 高 64 带包缓存 80 MiB，46 MiB ≈ 高 64 不带包缓存 45 MiB。最可能的情况是两次测量一次在序列化之后、一次在之前（或把高度标反了），原程序已删，无法确认。另有两个口径能把高 64 推到 78 MiB 附近：生成器用 setAll（88～96 MiB），以及在新 JVM 里第一张世界不预热、把注册表与类的一次性分配算进来（本程序不预热冒烟时 64 区块世界因此多出约 1 MiB，放到 4,096 区块上影响 < 3%，解释不了 32 MiB 的差）。

结论：原两数作废，以本节表格为准；以后报堆数字必须写明「是否含包缓存」「调色板形态」「是否预热」三项。

## 7. 局限与下一步

- 耗时在负载均值 26～82 的机器上测得，墙钟只能当上界。下一步：在空闲机器上用 `./gradlew :jmh-benchmarks:worldBench` 复跑一遍，JSON 里的 `loadAverageBefore/After` 低于核数的一半才算有效，替换本文 §3.2、§3.3 的墙钟列。
- 地形没有光源方块，块光照成本为 0；美术地图的火把、岩浆会增加块光数组与包体。P2 拿到第一张真地图后，用同一程序加一种「从 .synx 或 Anvil 读入」的地形复测。
- 懒算光照路径的墙钟高于 CPU（6.4 ms 墙钟对 4.9 ms CPU），未见线程池的并行收益，但负载下主线程被抢占也会造成同样的现象，空闲机器复跑后才能下结论；整图 relight 的 CPU 成本（1.4 ms/区块）只有懒算的 29%。这支持报告第 6 节「载入期整图算光照」的方案 B，也说明任何大世界都不应依赖懒算。
- 生成器用 `setAll` 会把非单值 section 变成直接调色板，堆 ×3、包体 +47%。烘焙器与任何 M3 生成器要么逐块 `set`，要么生成后 `optimize(SIZE)`；这条应进 P2 的验收判据。
- `CachedPacket` 在堆里留着未压缩的 `ChunkDataPacket`（每区块 19～25 KB，是压缩包的 8～10 倍）。.synx 方案要求发送路径只持有压缩字节，P2 ④ 的 JFR 判据之外，还应在测试里断言未改区块的发送不产生 `ChunkDataPacket` 对象。
